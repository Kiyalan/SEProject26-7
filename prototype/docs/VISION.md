# RepoPilot Vision 文档

> 课题：**#A8 GitHub 仓库问答与 Issue 分析系统**  
> 产品名称：**RepoPilot**  
> 文档版本：2026-07（反映当前原型实现进度与后续规划）  
> 适用对象：项目组全员、指导教师、阶段评审

---

## 一、我们在解决什么问题

开源维护者和项目团队每天面对大量重复劳动：新人要读懂陌生仓库、维护者要分类回复 Issue、文档与代码脱节、历史变更难以追溯。GitHub 提供了仓库托管与协作能力，但缺少面向「维护场景」的智能聚合层——把**代码理解、知识检索、Issue 处理、变更操作**放在同一套 Web 工作流里。

**RepoPilot** 的定位是：接入 GitHub 仓库之后，成为维护者与贡献者身边的 Web 智能助手，而不是替代 GitHub，而是在其之上补足「理解仓库」和「处理 Issue」的效率缺口。

---

## 二、产品愿景（一句话）

打造一个面向开源维护者与开发团队的 **Web 智能助手**：接入 GitHub 仓库后，可基于多版本知识库进行 What / Where / How 问答，自动分析 Issue 并生成回复建议；进阶能力包括代码定位、自动修复草案与 Pull Request 创建，最终形成「发现 Issue → 理解上下文 → 给出方案 → 落地变更」的闭环。

**产品形态**：以 **Web 应用** 为主（课题要求客户端为浏览器），不将桌面客户端或浏览器插件作为主交付物；插件可作为后续快捷入口扩展。

---

## 三、目标用户与典型场景

| 用户 | 典型场景 |
|------|----------|
| **开源维护者** | 批量处理 Issue、统一回复口径、了解近期代码变更 |
| **核心开发者** | 快速定位模块与配置、对比 commit 间差异、无终端完成简单 Git 操作 |
| **新贡献者** | 通过问答理解项目结构、阅读知识库摘要与 README |

---

## 四、核心价值

1. **降低理解仓库成本**——用知识库与问答替代反复翻目录、搜文件  
2. **提升 Issue 处理效率**——自动分类、生成可审阅的回复建议  
3. **保留可追溯的历史**——按 commit 建立知识切片，支持版本对比  
4. **减少终端依赖**——通过 GitHub API 完成同步、提交、建分支、开 PR  
5. **为自动修复铺路**——索引、检索、Issue 分析是后续 Agent 与自动 PR 的基础设施

## 五、功能需求全景与完成度

以下按课题 **基础功能** 与 **进阶功能** 分列，并标注截至当前的实现状态，便于评审与排期。

**图例**：✅ 已基本可用 · 🟡 有原型/部分实现 · ❌ 尚未实现

### 5.1 基础功能

| 编号 | 需求描述 | 当前状态 | 说明 |
|------|----------|----------|------|
| F-01 | Web 端 GitHub OAuth 登录 | ✅ | 真实 OAuth，读取用户有权限的仓库 |
| F-02 | 多仓库接入与列表管理 | ✅ | 拉取用户可见仓库，支持列表与详情 |
| F-03 | 仓库数据同步（README、Issue 等） | 🟡 | Issue、仓库元数据可实时拉取；无 Webhook 推送式同步 |
| F-04 | 知识库构建（目录、文档、源码索引） | ✅ | 从 GitHub 拉取文本文件，分块入库 |
| F-05 | 按 commit 保留多版本知识切片 | ✅ | 内容寻址去重；可选为最近 N 个 commit 各建快照 |
| F-06 | 历史版本对比（文件级 diff） | ✅ | 选定两个 commit，展示增删改与部分 diff 预览 |
| F-07 | 智能问答（What / Where / How） | 🟡 | 问题分类 + 关键词检索 + 可选 LLM；**尚无向量检索** |
| F-08 | 问答结果含代码/文件引用 | ✅ | 返回 citations（路径与行号） |
| F-09 | Issue 列表与筛选 | ✅ | 拉取开放 Issue，支持按 AI 分类筛选 |
| F-10 | Issue 智能分析（类型、摘要、建议回复） | 🟡 | 规则分类 + 知识库关联文件；**未深度使用 LLM** |
| F-11 | 知识库浏览（结构、模块、依赖） | ✅ | 目录树、语言分布、依赖解析、README 预览 |
| F-12 | 系统设置（GitHub / AI 配置） | 🟡 | 设置页为原型表单，**配置实际在 `.env`，未持久化到库** |
| F-13 | 无终端 Git 快捷操作 | 🟡 | 建分支、提交文件、创建 PR、自然语言触发；需 `repo` 写权限 |
| F-14 | 统一信息架构与可演示主路径 | ✅ | 登录 → 仓库 → 知识库 / 问答 / Issue 全链路可演示 |

### 5.2 进阶功能

| 编号 | 需求描述 | 当前状态 | 说明 |
|------|----------|----------|------|
| A-01 | 向量 RAG（Embedding 检索） | ❌ | 当前为关键词匹配；`chunk_blobs` 已预留去重结构 |
| A-02 | 多轮对话与历史会话持久化 | ❌ | 问答仅在当前页内存，刷新即失 |
| A-03 | Issue 自动回复到 GitHub（经人工确认） | ❌ | 仅「复制建议回复」，未调用 Issue Comment API |
| A-04 | Issue 与历史 Issue 的语义去重 | ❌ | 仅有规则级「重复」分类，无相似 Issue 检索 |
| A-05 | 基于 Issue 的代码定位与修复建议 | 🟡 | 可关联知识库文件；**无 patch 生成** |
| A-06 | 自动创建修复 PR（Issue → patch → PR） | ❌ | 详情页有「阶段三预览」；快捷操作可手动开 PR |
| A-07 | 多智能体协作（分析 / 检索 / 编码 / 审阅） | ❌ | 单链路：规则 + 检索 + 可选单 LLM 调用 |
| A-08 | 知识图谱（模块 / 接口 / 依赖关系图） | ❌ | 仅有模块列表与依赖标签，无可交互图谱 |
| A-09 | GitHub Webhook 实时同步 | ❌ | 设置页为占位 URL，后端未接 Webhook |
| A-10 | 后台任务队列（多仓库并发索引） | ❌ | 索引为同步 HTTP 请求，大仓库或 N 个 commit 会阻塞 |
| A-11 | 问答 / 分析指定历史 commit 版本 | 🟡 | 知识库可按 commit 查看；**问答仍默认 active commit，未在 UI 显式选择** |

### 5.3 非功能需求

| 编号 | 需求描述 | 当前状态 | 说明 |
|------|----------|----------|------|
| NF-01 | 同时管理多个 GitHub 项目 | 🟡 | 多仓库列表与按 `repo_id` 隔离数据已有；**无并发任务调度** |
| NF-02 | 数据隔离（仓库 / 用户） | 🟡 | 仓库级 SQLite 隔离；OAuth token 存前端，**无服务端用户表** |
| NF-03 | 安全（密钥不进 Git、最小权限） | 🟡 | `.env` + `.gitignore`；OAuth state 为内存集合，**生产需 Redis** |
| NF-04 | 可维护性与团队协作 | 🟡 | 分支规范在 README；团队仓库 `SEProject26-7` 待完全合并 |
| NF-05 | 响应式 / 移动端可用 | 🟡 | 侧栏可收起、窄屏浮层；**未做 PWA / 触控专项优化** |
| NF-06 | 可部署演示（非仅 localhost） | ❌ | 需配置公网回调、HTTPS、进程守护 |
| NF-07 | 存储效率（历史版本不爆炸） | ✅ | 内容寻址 blob，相同文件跨 commit 共用 |

## 六、当前整体完成度（诚实估计）

| 维度 | 完成度（约） | 一句话 |
|------|--------------|--------|
| 界面与信息架构 | **90%** | GitHub 风格、三栏布局、8 个核心页面齐全 |

**目标**：Issue 驱动的自动修复与 PR，体现课题差异化。

| 优先级 | 待办 | 价值 |

| P0 | Bug 类 Issue → 定位文件 → 生成 patch 草案 | 进阶核心 |

## 八、技术架构愿景

```
┌─────────────────────────────────────────────────────────────┐
│  React Web（RepoPilot UI）                                   │
│  登录 · 仓库 · 知识库 · 问答 · Issue · 设置 · 快捷 Git 操作   │
└───────────────────────────┬─────────────────────────────────┘
                            │ REST API
┌───────────────────────────▼─────────────────────────────────┐
│  FastAPI 后端                                                │
│  OAuth · 仓库/Issue API 代理 · 知识索引 · RAG · Issue 分析   │
│  Git 操作代理 ·（规划）Webhook · 任务队列 · Agent 编排        │
└───────┬─────────────────────────────┬───────────────────────┘
        │                             │
┌───────▼────────┐            ┌───────▼────────┐
│  SQLite（当前） │            │  GitHub API    │
│  内容寻址知识库 │            │  仓库/Issue/PR │
│  +（规划）向量  │            │  Webhook       │
└────────────────┘            └────────────────┘
        │
┌───────▼────────┐
│  LLM 服务      │
│  （可选 API）   │
└────────────────┘
```

**知识库数据模型（已实现要点）**：

- `content_blobs` / `chunk_blobs`：按内容哈希去重，节约空间  
- `repo_commits` + `commit_files` + `commit_chunks`：每个 commit 完整切片，共享不变内容  
- 页面展示摘要与结构；全文片段仅存库供检索

## 九、各阶段成功标准

### 阶段二答辩可接受标准

- [ ] 用户 OAuth 登录并管理多个仓库  
- [ ] 至少一个仓库完成知识库索引（含多 commit 可选）  
- [ ] 智能问答能回答 What / Where / How 并给出文件引用  
- [ ] Issue 分析展示类型、依据、建议回复与相关文件  
- [ ] 演示两个 commit 之间的文件对比  
- [ ] 文档（Vision、用例、迭代计划）与实现一致  

### 阶段三 / 课题完整验收标准

- [ ] 向量 RAG 或同等语义的检索增强  
- [ ] Bug 类 Issue 能生成可审阅的修复建议或 patch  
- [ ] 经确认后可创建 PR 并回链 Issue  
- [ ] 多仓库并发索引不阻塞前端（异步任务）  
- [ ] Webhook 或定时任务保持 Issue / 知识库 reasonably 新鲜  
- [ ] 可公网访问的演示环境

## 十、明确不做或延后的事项

- **桌面客户端、小程序**：非课题主形态，不纳入核心排期  
- **替代 GitHub 的全功能 Git 客户端**：仅做常见维护场景的 API 封装  
- **对任意公开仓库无需登录的分析**：可作为演示增强，非当前主线  
- **全自动无人值守合并 PR**：需人工审阅闸门，避免安全风险  

---

## 十一、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| GitHub API 限流 | 多 commit 索引失败或变慢 | 异步队列、指数退避、缓存 |
| LLM 成本与稳定性 | 问答 / 分析质量波动 | 检索摘要兜底；关键路径可配置模型 |
| 范围蔓延（Agent、图谱全要做） | 无法按期交付 | 严格 P0/P1/P2，先闭环再锦上添花 |
| 五人协作与 Git 不熟 | 合并冲突、重复劳动 | feature 分支 + PR + 飞书分工表 |
| 答辩环境网络 | 演示失败 | 预索引仓库 + 录制备用视频 |

## 十三、总结

RepoPilot 已经具备**可演示、可开发、可评审**的骨架：真实 GitHub 接入、多版本知识库、基础问答与 Issue 分析、GitHub 风格 UI。与课题文档中的**完整目标**相比，差距集中在「更聪明的检索与推理」「与 GitHub 的双向闭环」「自动化修复与 PR」以及「生产级并发与同步」。

后续开发应遵循：**先巩固阶段二 P0（向量 RAG、LLM Issue 分析、异步索引），再攻坚阶段三自动 PR 闭环**；避免在尚未稳定的核心链路上过早堆叠多 Agent 与知识图谱等演示型功能。
