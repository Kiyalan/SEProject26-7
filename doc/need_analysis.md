以下用 "目标项目" 代指需要处理的 github 仓库，用 "工具" 代指我们实现的 github 工具

核心需求：帮助用户
- 理解目标项目（面对尝试了解目标项目原理、实现的用户）
- 使用目标项目（面对使用该目标项目的用户）
- 更新目标项目（面对项目的维护者）

为了帮助用户达到这些目的，工具首先需要对目标项目进行处理和分析使得工具自己对该项目 "建立了良好的理解"（将原始项目结构化地转化为工具能够理解的子部分），在此基础之上，根据不同的目的（应用方法，更新迭代）来提供对应的建议。

因此工具的设计应当分为以理解项目为目的知识库构建和以应用项目为目的知识库消费

知识库构建的功能需求（具体地描述如何构建这个知识库）：
- 接入目标项目的 github 仓库：要求利用 API 获取项目的、文档、元数据，并以某种方式保存下来以便于后续对于目标项目的处理
- 按 "模块" 拆分目标项目（可能可以包含多级拆分，不同 "模块" 之间的关系只能是 “包含” 或者 “互斥”，不能是 "相交且不包含"）：要求根据仓库目录、README、代码内容来划分目标仓库为相对独立的 "模块"，并构建 “模块” 之间的关系（调用、依赖等）
- 基于模块的拆分结构，进一步构建 "实体" 的结构（鉴于大部分项目都是面对对象的，一个 "实体" 通常对应一个关键的类，工具辅助性的类不属于 "实体"）：要求对于一个 "实体"，分析清楚其提供的接口，了解其关键功能的实现原理；对于不同的 "实体"，分析清楚它们之间的继承、调用关系。
- 知识库的跨 commit 性：根据 git 的 commit 历史，形式上来说每一个 commit 版本的每一个 "模块"、"实体" 等知识单元都存一个对应的知识文档，储存上来说为了节约内存需要尽可能地公用 commit 之间共有部分的知识单元的文档
- 将上述的分析结果以某种方式保存下来，供消费端取用相关知识

知识库消费的功能需求
- commit 更改分析（便于用户理解目标项目的变更历史）：要求支持分析 commit 主线迭代趋势，分析两个不同 commit 之间的具体差异
- issue 问题分析与解答（便于用户使用过程中解决碰到的 issue）：要求根据 issure 描述和下面的jiaoliu，确定 issue 发生的原因（用户使用不当？目标项目刻意设计或者权衡的结果？目标项目确实存在问题？）。
	- 如果是用户使用不当则需要提供正确的使用方法；
	- 如果是目标项目刻意设计，结合具体的知识库来解释如此设计的原因；
	- 如果是目标项目确实存在问题定位存在问题的具体位置（"模块"、"实体"），并根据当前项目提供一份正确的、形式统一的 fix。
- 普通问答，包括目标项目的结构、设计、原理相关问题询问（便于用户理解整个项目的具体实现）：要求根据用户的疑问和知识库提供解答。

前端页面设计对应到如上两个部分应当包括
- 为了构建知识库需要的：用户登录页面（并在后端给用户分配知识库空间），仓库页面（绑定 github，用户选择需要进行解析的仓库并查看（后端进行知识库构建并储存））
- 为了用户的消费需要的：commit 分析页面，issure 分析页面，普通问答页面
